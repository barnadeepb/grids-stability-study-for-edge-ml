# Results

This folder is generated by `scripts/run_experiment.py` -- nothing here is
hand-edited. Re-running the script overwrites everything in this folder.

## Files

| File | What it is |
|---|---|
| `model_comparison.csv` | The full metrics table: one row per model, every column described below. |
| `metric_accuracy.svg` / `.png` | Classification accuracy, all models, one bar chart. |
| `metric_precision.svg` / `.png` | Precision (of everything predicted "unstable," how much actually was). |
| `metric_recall.svg` / `.png` | Recall (of everything actually "unstable," how much was caught). |
| `metric_f1.svg` / `.png` | F1 score (the balance of precision and recall). |
| `metric_latency_us.svg` / `.png` | Inference latency per prediction, with the IEC 61850-5 protection timing budget marked. |
| `metric_size_kb.svg` / `.png` | Trained model size on disk. |
| `tradeoff_accuracy_vs_latency.svg` / `.png` | Accuracy plotted against latency -- the main "is this model deployable" chart. |
| `tradeoff_accuracy_vs_size.svg` / `.png` | Accuracy plotted against model size -- same idea, footprint instead of speed. |

SVGs are the print-quality vector versions (used in the paper); PNGs are for
quick viewing. Both are regenerated together and always match.

## How to read the CSV columns

| Column | Meaning |
|---|---|
| `model` | Model name. |
| `accuracy`, `precision`, `recall`, `f1` | Mean of that metric across the evaluation splits (see main README for how many splits each model used). |
| `*_std` | Standard deviation of the same metric across those splits -- how much the number moved from one random split to another. |
| `latency_us` | Mean time to make one prediction, in microseconds, averaged over many repeated calls. |
| `latency_us_std` | Standard deviation of that timing. |
| `size_kb` | Size on disk of the trained pipeline (feature scaler + model), in kilobytes. |
| `trained_on_n_samples` | How many rows the model was actually trained on. This is 8,000 for every model except TabPFN (5,000 -- see main README for why). |
| `best_params` | The hyperparameters selected by the tuning step for that model. Empty for TabPFN, which has nothing meaningful to tune here. |

## What the headline numbers mean

The single most important context for every chart here is the **~4
millisecond protection-critical timing budget** (IEC 61850-5, Type 1A
messages -- see main README). It's marked directly on the latency bar chart
and the accuracy-vs-latency trade-off chart. A model to the right of that
line is not a viable candidate for a real-time protection decision,
regardless of how accurate it is.

Reading the charts with that budget in mind:

- **Random Forest** is the model most likely to be reached for by default in
  academic ML-for-grid work, and it's the wrong choice here: it misses the
  latency budget by roughly 3.5x, is the second-largest model on disk, and
  is *less* accurate than Gradient Boosting.
- **Gradient Boosting (XGBoost)** is the best candidate actually found in
  this comparison: highest accuracy of every model inside the budget, a
  small on-disk footprint, and comfortably fast.
- **TabPFN** scores the highest raw accuracy of all seven models, but misses
  the latency budget by roughly four orders of magnitude and is ~445x
  larger on disk than Random Forest. It is included specifically to show
  this -- see the main README's TabPFN section for the additional
  (non-latency) reasons it's a poor fit for this deployment setting.

## Reproducing these exact numbers

See the main [README](../README.md) for setup and running instructions.
Six of the seven models are fully reproducible from a fresh clone with no
account of any kind. TabPFN is optional and requires its own account -- the
script skips it automatically if you haven't set that up, and everything
else in this folder is unaffected either way.
